# 02 核心概念

本章把引擎里最重要的几个概念用大白话讲清楚：图纸与实例、节点与令牌、任务与已办、
变量、事件、时钟。理解了它们，后面每一章的具体操作都会顺理成章。

## 图纸与实例

- **流程定义（ProcessDefinition）** 是图纸：节点、连线、条件、变量声明构成的一张有向图。
  图纸经过 `deploy` 发布进引擎，**发布后不可变**——你只能发新版本，不能改老版本。
- **流程实例（instance）** 是照着图纸跑的一笔具体业务：张三今天报销的那一单。
  一次发布可以被发起任意多次，每次发起各走各的。

**快照**是两者的连接点：发起实例时，引擎把图纸整个抄一份存进实例。之后图纸发了新版，
**在跑的老实例仍按它发起时的那一版图纸走完**，不会被新版本影响。想发起就用新版本，
不必等老实例清零。

图纸有版本号：`code + major + revision` 三段定位一个版本。改动不破坏兼容时
revision 自动加一；结构破坏性变更（比如删了节点、改了条件语义）会判 major 加一。
`deploy` 会返回一个判定报告，告诉你这次变更算哪种、破坏在哪（第 4 章细讲）。

## 节点与令牌

图纸上的每个方框是一个**节点（node）**，八种内置类型（start / end / user_task /
service_task / branch / cc_task / call_activity / wait）各有各的行为（第 3 章逐个讲）。

**令牌（token）** 表示「流程当前走到了哪」。可以把它想成一枚在图上移动的棋子：

- 实例发起时，一枚令牌落在 start 节点上，流程开始；
- 令牌每到一站，该节点的行为被激活（人工节点生成待办、系统节点执行动作、等待节点开始等消息）；
- 节点办完，引擎按出边的条件求值选路，令牌移到下一站；
- 令牌到 end 节点，这一支结束；所有令牌都到终点，实例完成。

**并行不需要专门的「并行网关」**：一个节点有多条**无条件**出边，令牌到达后就会
沿着每条出边各复制一枚走——这就是分流。反过来，多条入边汇聚到一站时怎么算「到齐」，
由节点的汇聚策略（`advance_policy`）决定：

- `any`：任意一条入边有令牌到达即激活（先到先走，同批到达的兄弟臂会被竞速取消）；
- `all`：所有入边都到达才激活（典型的并行汇聚）。

令牌状态只有前进没有回退：`unfinished`（在途）→ `finished`（已过站）/ `cancelled`
（被取消）/ `revoked`（被撤回）。查实例的令牌列表用 `engine.history.tokens(instance_id)`。

## 任务与已办

**任务（task）** 是人工节点生成的待办：谁办、办什么节点、什么时候建的。
第 6 章讲的认领、办结、驳回、转办、加签都作用在任务上。

**已办（TaskHistory）** 是任务的归档，有两个铁律：

1. **只追加，不修改**。一个任务被办结、被取消，就归档成一行已办记录，原记录不动。
2. **驳回复活＝新任务**。驳回回退后重新生成的待办是**新的任务行**（带 `cause_token_id`
   溯源），不是把旧任务改回待办。所以「某人办过几轮」要数已办行，不是数任务。

每次归档都带 `acted_by`（实际办理人）——谁在什么时间以什么结果（`outcome`：
agree / reject / transfer / assist……）办了这一步，全程可审计。

## 变量

**流程变量**是这笔业务的业务数据：金额、标题、意见……发起时通过 `variables` 传入，
之后可以在几处被写：

- 办结任务时顺带写入（`complete(..., variables={...})`）；
- 系统节点 / 自定义节点的行为里写（`ctx.variables.update(...)`）；
- 外部受控修改（`runtime.update_variables`，带门槛与留痕，第 7 章）。

变量供**条件与表达式**消费：连线条件读它来选路，取人表达式读它来找人（第 5 章）。
每一次外部写入都有**变量血缘**（`variable_history`）——改前值、改后值、谁改的、为什么改。

图纸里可以声明变量（名字、类型、示例值）：声明不约束运行时传参，但它是校验器的
依据——条件里引用一个没声明也没保留的变量名，设计期就报错，而不是留到运行时炸。

## 事件

**事件（event）** 是引擎对外发声的唯一通道。内核不做推送、不调回调——每次有意义的事
发生（实例启动、节点进出、任务创建与办结、超时触发、故障产生……），引擎就在
**outbox** 表里落一条事件记录，由你的应用自己拉取消费（第 9 章讲怎么消费）。

事件的两个关键承诺：

- **至少一次**：事件不会丢；配合按事件 id 幂等去重（`IdempotentSink` 参考实现），消费侧可以做到恰好一次的效果。
- **全序**：同一实例的事件按时间与 id 排出确定的先后顺序，回放时不会随机跳。

引擎自发的事件名是**枚举全集**（`DomainEvent`，40+ 个成员）——你可以按枚举编程，
不必担心漏掉新事件名（宿主自定义事件名不受枚举约束）。

写入粒度可配（`EngineConfig.history_level`）：`full`（全记，默认）/ `audit` / 
`activity`（只记 process_ / node_ / incident_ 前缀）/ `none`。选 activity 的宿主
拿不到任务级事件——按需取舍。

## 时钟

引擎内一切「现在几点」都走同一个时钟源：`EngineConfig.now`（默认系统 UTC 时间，
统一 naive UTC）。超时计算、时限判定、事件时间戳、表达式里的 `now` 全部以它为准。

测试时注入一个假时钟（`EngineConfig(now=fake_clock)`），就能确定性地测超时与
时限逻辑——不必真等时间过去，也不怕测试跑得慢导致断言漂移。

## 概念速查表

| 概念 | 一句话 | 相关 API |
|---|---|---|
| 定义 | 图纸：节点+连线+条件，发布后不可变 | `repository.deploy` / `get_definition` |
| 实例 | 照图纸跑的一笔业务 | `runtime.start_process` / `get_instance` |
| 快照 | 发起时抄走的图纸副本，老实例按老图纸走完 | （内部机制，无需操作） |
| 令牌 | 在图上移动的棋子，表示流程走到哪 | `history.tokens` |
| 任务 | 人工节点的待办 | `task.list_tasks` / `task.complete` |
| 已办 | 任务归档，只追加、驳回复活是新任务 | `history.task_history` |
| 变量 | 业务数据，供条件与取人消费 | `runtime.variables_of` / `variable_history` |
| 事件 | 引擎对外发声的唯一通道，至少一次 | `history.events` / `OutboxConsumer` |
| 故障单 | 出技术故障后实例挂起，等人修 | `runtime.list_incidents` / `resolve_incident` |

还有一个概念提前打个招呼：**故障单（incident）**。引擎把运行错误分成业务错误与
技术故障两类——业务错误（比如条件里引用的变量不存在）表现为条件不满足、走默认边；
**技术故障**（比如 handler 代码抛异常、表达式语法错）则让实例**挂起**（suspended）
并产生一张故障单，等管理员用五个动作之一处置（重试 / 跳过 / 取消 / 失败 / 恢复，
第 7 章细讲）。设计哲学是：出了技术问题让流程**停下来等人**，而不是静默走错路。
