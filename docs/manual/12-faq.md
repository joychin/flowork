# 12 踩坑与 FAQ

每条都是真实踩过的坑：现象 → 原因 → 正确做法。遇到问题先扫这一章。

## 流程定义与路由

**Q：我画了两条出边，想的是「二选一」，结果两条都走了？**
多条**无条件**出边＝并行分流（引擎没有「排他网关」概念）。要按条件二选一，
用 branch 节点 + 出边挂 `condition` + 一条 `default` 边。检查办法：
`route_decisions` 里看每条边的求值记录。

**Q：branch 的条件全不中，流程卡住不动了？**
全不中且没有默认边＝**技术故障**：命令回滚、实例挂起并出故障单——不是安静
等待（变量后来变了也不会自动重估）。给 branch 配一条 `is_default: true`
的兜底边是常规做法；真要「等某个条件成立再走」，用 wait 节点（等消息 /
等时长）。已经挂起的：修好条件的数据后 `resolve_incident(resume)` 会用新值
重新选路。

**Q：改了模板重新 deploy，在跑的实例怎么没按新逻辑走？**
快照语义（第 2 章）：实例发起时抄走了当时的图纸，**老实例按老图纸走完**。
想让新发起用新逻辑，deploy 新版本即可（老实例不受影响）；想「在跑的也切过去」
没有这种操作——那是数据迁移问题，不是流程引擎问题。版本与发布的完整语义
（幂等去重、破坏性判定、维护分支）见第 4 章。

**Q：明明只是加了个节点，怎么被判成破坏性变更（major 加一）了？**
R4 拓扑规则看**入边集合**：往中间插节点会改掉后继节点的入边，删除/回退同理。
业务上确认语义兼容的话，`allow_minor_reason` 带理由覆盖即可（第 4 章）。

**Q：单人节点（assignee）配了会返回多个人的表达式，发起就报错？**
这是**运行期**拦截的错误：单人位解析出多人＝技术故障（挂起+故障单，发起命令
整笔回滚）——取人表达式在设计期数不出人头。要多人各自办就用 `assignees` +
`multi_instance`（会签），或者候选池 `candidate_users` / `candidate_groups`
等认领。

**Q：条件里引用了变量，设计期校验就报 unknown？**
条件能引用的名字＝图纸**声明过的变量** ∪ 保留标识符（`initiator` / `now` /
`prev_task`……）。这是防拼写错误的第一道防线——把变量补进 `variables`
声明，或者检查名字拼对了没有。

## 取人与候选

**Q：`list_tasks(candidate=...)` 查出来的任务，有的已经有人办了？**
候选查询的口径是「与我相关的候选」，**默认含已被他人认领的任务**（还能看见
池子里发生了什么）。要「还没被抢走的」，组合 `assignee=""` 查未认领。

**Q：`manager_of(initiator)` 找到的人不对？**
两个可能：①目录里配了**委托**（delegations）——取人解析时委托替换生效，
上级的待办会落到被委托人头上（这是特性，不是 bug）；②YAML / 目录数据里
`manager` 链配错了。查法：直接调 `org.manager_of(user)` 看原始返回。

**Q：候选组任务，认领时提示无法判定归属？**
组引用（`role:xxx` / `org:xxx`）认领时按**组织目录**现场判归属——
没配目录（`EngineConfig.org`）组候选恒不命中。CLI 场景要带
`--org org.yaml`；嵌入式确认 engine 挂了目录。

## 会签与表决

**Q：会签里有人转办了，票数怎么算？**
**票随人走**：转办人不算已参与，被转办人办了才算这一票。同理
`auto_pass`（自动通过策略命中）算推进但**不算表决**——「谁真正投过票」
与「谁碰过这个节点」是两个口径，审计名单时注意区分。

**Q：会签被驳回两次，重提后的名单越来越长？**
不会。驳回复活名单**圈定最近一轮**——只有最近一轮参与的人重新进名单，
多轮驳回不膨胀。如果你观察到名单异常，查一下是不是把协办 / 传阅 / 咨询行
也算进「参与」了（这些不占票、也不进复活名单）。

**Q：会签门槛写「过半」，5 人 3 票同意怎么没过？**
严格过半写精确式 `task.approve_count * 2 > task.item_count`（5 人要 3 票：
3*2=6 > 5，是过的）；`task.approve_count * 100 >= task.item_count * 51` 是
「至少 51%」，分母超过 100 时与严格过半会差一票。注意 `item_count` 是
**应办人数**——加签会增加分母（同步加一）；转办换人**不改**分母，那一票
转由被转办人补投。对不上时先查应办数被什么动作改过。

**Q：撤回自己的已办，被拒绝说下游有进展？**
撤回会取消下游，所以下游已有**真实表决**（agree / reject 的已办）或工作节点
（审批 / 子流程）已完结的令牌就拒绝，提示改用驳回走正门——协办、咨询、
自动通过这些行不算进展。能撤的窗口＝「下游还没人真办过」。另外同一票只能撤一次。

## 超时与等待

**Q：超时配了但一直没触发？**
超时是 Job，要有东西驱动 `tick`：单进程确认 `engine.jobs.start()` 开了
（web 形态默认开）；多副本确认有独立 worker 在跑 `flowork tick`。
另外**暂停期间定时器冻结**（顺延不丢弃），实例在 paused 状态下超时不触发
是设计行为。

**Q：转办 / 改派之后，超时到点时间变了吗？**
没变。时限 Job 跟随「等待实体」重绑到新任务行，`run_at` 保持原值——
转办不重置时限。要是业务上要「换人重新计时」，用驳回或撤回重走。

**Q：消息发出去了，等待节点没动？**
按顺序查三件事：①订阅在不在——`messages.waiting(name=...)` 反查；
②关联键对不对——订阅声明的 `correlation_key` 求值结果与发布的
`correlation_key` 参数**字符串相等**才命中（防串单，常见错位是一边有
业务单号一边没有）；③缓冲 TTL——没有等待者时消息进缓冲，过期就丢了，
回查 `messages.list_messages(...)` 看状态。

**Q：`start_on_message` 发布消息后变量里没有载荷？**
消息启动**不整包合并**载荷——声明 `input_mappings`
（如 `{"order_id": "payload.order_id"}`）显式映射（表达式在 `payload.*`
上下文求值）。等待节点的 `output_mappings` 同理，不声明才是全量合并。

## 事件与集成

**Q：订阅方收不到 task_created 之类的事件？**
查 `history_level`：选了 `activity` 只记 `process_` / `node_` / `incident_`
前缀——**任务级事件在该档被吞**。要任务通知至少开 `audit`（或默认 `full`）。

**Q：同一事件收到了两次？**
投递语义是**至少一次**，重试与多消费者副本都可能造成重复——消费侧必须按
事件 id 幂等。用参考实现 `OutboxConsumer` + `IdempotentSink` 就自动去重了。

**Q：`wait.result` 写在下游分支的条件里，校验报错？**
`wait.*` 词汇**只能用在等待节点的直接出边**上——隔一个节点上下文就丢了。
把条件挪到 wait 节点的出边上。

## 技术故障排查

**Q：实例变成 suspended，怎么办？**
`suspended` ＝ 出了技术故障在等人。`runtime.list_incidents(instance_id=...)`
看故障单（错误类、消息、定位到节点），修根因后 `resolve_incident` 选动作
（第 7 章五动作表）。注意 retry 后**要重办**导致失败的那一步——失败命令
整体回滚了，原任务还在待办里。

**Q：表达式求值报错，流程为什么不走默认边？**
求值错误＝**技术故障**（挂起+故障单），不是「条件为假」。语法错、类型错、
函数 null 传播炸了都属于这一类。区分：条件**算出来是 false** 走默认边；
条件**算不出来**是故障。「查无」按温和降级处理——但只限两类：判断面事实
查无（`prev_task` / `node()` 没查到）与人查无（取人函数返回空，贡献为空）；
**变量缺值是求值错**（挂起+故障单），不是温和场景。

**Q：CEL 里调自己的函数报 no matching overload？**
两类常见：①把原生 `bool` / `None` 直接喂进 CEL 运算——经注册面返回的值会
统一抬升，但函数**参数侧**收到的已是 CEL 值，null 要先
`x != null ? ... : ...` 判空；②谓词函数（返回 bool）写进了取人位——
取人位只收人 / 人列表 / 组，谓词属于条件位，validator 会拦。

## 还是不行？

排查的通用三板斧：

1. `history.trace_instance(iid)`——整实例时间线，卡在哪一目了然；
2. `history.route_decisions(iid)`——每个决策点的公式与求值结果；
3. `runtime.list_incidents(instance_id=iid)`——有没有挂着没处理的故障单。

三样都干净还解释不了行为，带着这三份输出去看 spec 对应章节
（`docs/product/kernel-v2/spec.md` 有每条语义的精确定义与论证）。
