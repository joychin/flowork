# flowork 审批网关 v1 · 原型设计说明

> 第 4 篇。原型文件：[prototype/index.html](prototype/index.html)（单文件、零依赖，浏览器直接打开）。本文记录信息架构决策、交互映射、演示脚本与原型要验证的假设。

## 1. 信息架构（IA）

控制台五个一级入口，对应四个角色的一件事：

| 入口 | 角色 | 回答的问题 |
|---|---|---|
| 审批收件箱 | 老周 | "AI 要干什么？我批不批？" |
| 申请中心 | 小陈 | "我要发起一个申请，它在哪了？"（人侧入口，与 Agent 请求同管道） |
| Agent 名册 | 林姐 | "有哪些 AI 在岗？各自被授权干什么？" |
| 策略中心 | 林姐 | "制度怎么变成机器规则？改了会怎样？" |
| 审计回放 | 何敏 | "谁批的？按哪版制度？出了事怎么讲清楚？" |
| 组织目录 / 设置 | 林姐 | v1 极简目录内置，v1.1 对接企业真实目录 |

**IA 决策与理由**：

1. **收件箱是默认首页**——治理产品的日活来自审批动作，不是来自看板；老周的高频使用是整个系统对林姐/何敏的价值来源（没有审批流量就没有审计数据）。
2. **首页放四个统计卡**（待我审批/自动通过占比/平均用时/超时升级）——把"自动通过占比"放在首屏，是给管理员的第一眼价值主张：*这台机器替你挡掉了多少噪音、只把真正需要人的送到你面前*。
3. **AI 与人在全 UI 用可区分视觉**（紫色 🤖 徽章 vs 实名）——"AI 提议、人签字"的双链归因是产品核心心智，必须在每个界面反复强化，不是审计页的专属。
4. **policy 版本 chip 贯穿所有视图**（收件箱详情、名册、审计链都显示 v12/v11）——"按哪版制度"是审计问题的答案，让版本可见性成为肌肉记忆。
5. **策略中心把"规则表 / diff / 模拟器 / 版本时间线"放在一屏**——管理员的决策回路是"改规则 → 看 diff → 模拟验证 → 发布"，四步不换页。
6. **申请中心与收件箱并列在人侧第一位**——人的申请（报销/请假）经模板表单汇入同一引擎：这是冷启动策略的产品化（人类日常流量先养活收件箱），也让"人提的"和"AI 提的"在收件箱/审计里天然混排（🙋 与 🤖 徽章同屏），把"组织授权层覆盖所有 actor"变成肉眼可见的事实。
7. **IM 卡片形态内嵌在收件箱详情里**（飞书样式 mock）——审批人的主战场在 IM 不在网页，控制台里的卡片预览同时服务于：管理员理解"审批人会看到什么"、演示时讲一致的故事。

## 3. 演示脚本（原型 = 3 分钟版，工程版见 02-需求规格 §4 DoD）

1. **开场（收件箱）**："这是老周的早晨：3 笔待办，AI 已经自动处理了 38 笔低风险退款——只把需要人的送来。"点开 ¥86,000 退款：紫色 AI 徽章讲清"谁在请求"，policy v12 chip 讲清"依据什么"。
2. **人机同管道（申请中心）**：切到申请中心，替小陈提交一笔报销 ¥1,200——提交后自动跳回收件箱并选中：它和 AI 的退款请求并排躺着，证据链前三步是"🙋 小陈提交 → AI 预审通过 → 等待周主管"。一句话："人和 AI 走同一条授权管道，审计同一口径。"
3. **驳回回路**：点驳回 → 意见留空被拦 → 填"缺物流凭证"+拒绝码 → 确认。强调 toast 里的两件事：意见回传 Agent、整改重提挂 supersedes 链。再切到审计页选 REQ-0038 看昨天的驳回与今晨的重提如何成链。
4. **自动通过与限额**：策略中心 → 模拟器选"销售Agent-B（T0 试用）"金额 86000 → 展示"agent 限额优先于动作规则，强制人审"；再选客服Agent-07 金额 120 → 自动通过。一句话："信任档就是 AI 的试用期。"
5. **制度版本**：切 v13 草稿看 diff → 讲"在途按旧版完成、新请求按新版"（快照隔离）→ 版本时间线回答审计的"按哪版制度"。
6. **收尾（审计页）**：选 REQ-0042 展开完整证据链——"监管问'谁批的'，答案在这一屏：AI 提议、张三批准、依据 v12 规则②，永久只追加。"点导出 CSV。
7. **彩蛋（接入示例弹窗）**："而这一切的接入成本是一行代码。"

## 4. 原型要验证的假设（拿去见种子用户）

| # | 假设 | 验证方式 | 证伪信号 |
|---|---|---|---|
| H1 | 审批人 30 秒内能看懂卡片并做出决定 | 给 3 个真实业务负责人走演示脚本第 1 步，观察是否需要解释 | 反复问"这 AI 是谁/这金额哪来的" |
| H2 | "风险×SLA"是审批人认可的列表排序 | 让审批人指出想先处理哪条，对比排序 | 多数人想按提交时间/业务线排 |
| H3 | 管理员理解"agent 限额优先于动作规则"的求值顺序 | 演示脚本第 3 步提问复述 | 普遍预期规则表优先于信任档 |
| H4 | "自动通过占比"是管理员的核心价值感知 | 观察首屏四个统计卡哪个引发评论 | 无人评论自动化，只关心待办 |
| H5 | 审计证据链展示足以回答监管式提问 | 给合规角色看演示脚本第 5 步，问"还缺什么" | 要求补"业务背景/单据附件"等 BPM 重字段 |
| H6 | 试用期/信任档隐喻被接受 | 管理员是否自然使用"上岗/停用"词汇 | 要求改成纯技术参数（QPS/额度）表述 |
| H7 | 人机混排收件箱被接受且不造成困惑；人侧申请的"AI 预审"被感知为价值 | 演示脚本第 2 步后询问审批人与员工双方感受 | 审批人要求把"人提的"和"AI 提的"分成两个入口/列表 |

## 5. 视觉与后续

- 视觉基线：中性灰白底 + 靛紫强调（与 AI 徽章同族）、风险四色（crit/high/med/low）+ 自动通过蓝、等宽字体承载一切 ID/动作名（它们是协议的一部分）。
- 控制台与现有 designer（流程设计器）的关系：同一 FastAPI 服务的两个路由组（`/api/console/*` 与 `/api/definitions*`），部署上同源；后续在控制台加"查看该请求命中的流程定义"跳转设计器，形成治理（运行面）↔ 设计（制度面）的双向闭环。
- v1.1 原型迭代方向：CS108 报告模板预览、信任爬坡建议流（策略引擎推荐提额/降档）、组织目录对接视图。
