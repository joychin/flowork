# flowork 审批网关 v1 · 功能设计

> 第 3 篇。锚定仓库现状设计扩展点：引擎已有 `ProcessEngine.execute`（乐观锁命令管线）、`RuntimeService/TaskService/HistoryService`、`Jobs` CAS 超时、`EngineConfig.notifier`（现 noop）、web 设计器路由组（`/api/definitions*` 等）。**新增能力全部走新模块 + SPI，不改引擎核心**（满足 AGENTS.md 硬约束 2/3/8）。

## 1. 模块拓扑

```
flowork/
├── mcp/                 ★新增：MCP server（stdio+HTTP），薄工具面
├── authorization/       ★新增：agent 身份注册、凭证、风险策略（版本化）
│   ├── agents.py        agent_principal / credential / 生命周期
│   ├── policy.py        策略 DSL、求值器、版本发布（diff 复用 definitions 层交互）
│   └── directory.py     极简目录（用户/角色/主管），实现 OrgDirectory SPI 适配
├── gateway/             ★新增：approval request 应用服务（把 propose 翻译成引擎实例）
│   └── service.py       propose/wait/status/approve/reject/delegate/submit_application 用例编排
├── notifier/            ★新增：Notifier SPI 实现（webhook + 钉钉 + 飞书卡片）
└── web/
    └── console.py       ★新增：控制平面路由组 /api/console/*（收件箱/agents/policies/audit）
```

依赖方向：`mcp → gateway → {authorization, engine}`；`web/console → gateway`。gateway 是唯一的应用服务层，MCP 与 REST 共用（保证 US-105 行为一致）。

## 2. 核心概念与数据模型

### 2.1 新增实体（表）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `agent_principal` | id, name, owner, status(trial/active/suspended), trust_tier, created_at | 上岗证本体（US-301） |
| `agent_credential` | agent_id, token_hash, issued_at, revoked_at | 只哈希存储，明文仅签发时一次 |
| `policy_version` | id, version_no, rules(JSON), published_by, published_at, status | 不可变；`active` 指针单行表 `policy_pointer` |
| `approval_request` | request_id, agent_id, action, payload(JSON), idempotency_key, policy_version_id, status, supersedes_id | 面向 agent 的请求台账；`engine_instance_id` 关联流程实例 |
| `application_type` | code, name, fields(极简 schema：文本/数字/金额/附件), process_ref, version, published_by | 人侧申请模板（报销/请假等），版本化复用定义发布范式；`submitter` 见下 |
| `audit_event` | request_id, ts, actor(kind=human/agent), event, detail(JSON) | 只追加；与引擎 TaskHistory 并行，用于控制台检索（避免跨实例 join） |

**双链归因**：approval_request 上 `proposed_by_agent`（agent_id+版本+凭证指纹），每级审批在引擎 TaskHistory 已有 `acted_by`；audit_event 统一两者视图。这是对"谁批的/按哪版制度"审计问题的直接物化（NFR-04/05）。

**提交者多态（人机统一）**：`approval_request.submitter` 为 `{kind: agent|human, id}`——Agent 提议走 `proposed_by_agent`；人发起（报销/请假等）走 `submitted_by_user`（directory 用户）。audit_event 的 `actor(kind)` 本就双态，收件箱/IM 卡片/审计视图天然统一，无需分支逻辑。人侧与 Agent 侧的两点语义差异：①路由来源不同——人侧由 `application_type.process_ref` 的流程定义决定（金额条件是流程网关），不经风险策略求值；②责任语义不同——人本身就是最终责任人，无信任档/限额概念。

### 2.2 策略 DSL（v1 刻意收窄）

```jsonc
// policy_version.rules —— 有序规则表，首个命中生效；兜底 deny
{
  "rules": [
    {
      "when": { "action": "refund.customer", "amount_gt": 50000 },
      "route": { "kind": "approval_chain",
                 "participants": [ {"type": "role", "value": "finance"}, {"type": "user", "value": "u_shop_manager"} ],
                 "countersign": "all", "sla_minutes": 120,
                 "escalate": {"type": "direct_manager", "levels": 1} } },
    { "when": { "action": "refund.customer", "amount_lte": 500 },
      "route": { "kind": "auto" } },
    { "when": { "action": "infra.prod_migration" },
      "route": { "kind": "approval_chain",
                 "participants": [ {"type": "role", "value": "oncall_engineer"} ],
                 "sla_minutes": 60 } }
  ],
  "default": "deny"
}
```

- 求值顺序：**agent 状态检查（停用→拒）→ agent 限额（日上限/单笔额度，超限→人审）→ 规则表 → default**。
- 条件类型 v1 仅两种：`action` 精确匹配 + 数值比较（`amount_gt/amount_lte`，取值路径默认 `payload.amount`，可配 jsonpath）。表达式引擎不引入新能力（`expr/` 沙箱留给 v1.1 的通用条件）。
- **路由到流程定义的映射**：每条 `approval_chain` 规则编译为一个流程实例模板（开始→审批节点[会签/SLA/升级]→结束），由 gateway 启动实例；agent 语义（proposed_by/回执）通过实例变量注入。策略版本 → 编译产物缓存，与定义快照隔离语义对齐（在途按发起时版本）。

## 3. MCP 工具面（协议层首版动词集）

| 工具 | 参数 | 返回 | 权限 |
|---|---|---|---|
| `flowork_propose` | action, payload, idempotency_key?, context?(trace 等) | request_id, status(auto_approved/pending/rejected), route 摘要, rejection?(结构化) | agent 凭证 |
| `flowork_get_status` | request_id | status, current_step, pending_participants, route | agent 凭证（限本人请求） |
| `flowork_wait_for_result` | request_id, timeout_seconds(≤300) | 终态或 pending | agent 凭证 |
| `flowork_list_my_approvals` | status?, limit | 待办列表（人类审批人经 MCP 客户端查询用） | 用户身份 |
| `flowork_approve` | request_id, step_id, comment? | ok + 新状态 | 用户身份 |
| `flowork_reject` | request_id, step_id, comment, reason_code? | ok + 新状态 | 用户身份（意见必填，FR-203） |
| `flowork_delegate` | request_id, step_id, to_user | ok | 用户身份 |

设计纪律：**工具面刻意薄**（7 个）。BPM 高级语义（加签/转办/会签策略）不上 MCP——那是控制台与 REST 的事；agent 只需要"提交-等待-查状态"三件事 + 审批人侧三个动作。token 预算友好（AGENTS.md AI 友好设计原则）。

## 5. 关键时序

### 5.1 提交→自动通过（FR-105，P95<200ms 路径）

```
Agent ──flowork_propose──▶ mcp ─▶ gateway
   gateway: 鉴权(agent_credential) → 求值策略(authorization.policy)
        ├─ 命中 auto：直接写 approval_request(status=auto_approved, policy_version_id)
        │   + audit_event ×2(proposed/rule_hit) → 同步返回 approved
        └─ 命中 approval_chain：编译为流程实例(RuntimeService.start_instance)
            → 引擎推进到审批节点 → Notifier 投递卡片(钉钉/飞书) → 返回 pending+route
```

### 5.2 卡片审批（US-201）

```
飞书卡片按钮 ──回调──▶ notifier(验签) ─▶ gateway.approve(acted_by=用户)
   → TaskService 办件（引擎内乐观锁）→ 会签计数/出口判定
   → 终态时：audit_event(终态) + 回执通道(wait 长轮询唤醒 / webhook)
   → 卡片翻转（回调平台更新卡片，防重复点击）
```

### 5.3 驳回整改回路（US-103/场景1）

```
财务驳回(comment=缺物流凭证) → 终态 rejected
   → agent 收 flowork_wait_for_result = {rejected, rejection:{comment, code}}
   → agent 补参数 → flowork_propose(idempotency_key=新, supersedes=旧rid)
   → 新单 audit_event 关联 supersedes 链（审计侧可看"第2次提交"）
```

### 5.4 超时升级（US-206，复用现有 Jobs）

审批节点 SLA 120min → Jobs 超时触发（CAS 认领恰一次）→ 参与者升级为 DirectManager(发起审批人的上级) → Notifier 双向通知（原人"已升级"、新审批人新卡片）。

### 5.5 人发起报销（US-601/603，人机统一管道）

```
小陈 ──POST /applications(app.expense, {事项, 金额2380, 附件})──▶ gateway
   gateway: 提交者归因 submitted_by_user(小陈) → application_type(v3) 字段校验
        → 直接以模板流程定义启动实例（不经风险策略求值）：
          [AI 预审(发票核验Agent) → 直属主管 →(金额>1000 网关)→ 财务]
   AI 预审节点：通过 → 推进到人节点；不通过 → 直接驳回（原因回传小陈）
   人节点：与 Agent 请求同一收件箱 / IM 卡片 / SLA 升级 / 审计留痕
```

与 Agent 路径（5.1）的差别只有入口与路由来源：**汇入点之后的管道完全同一**——这是"人和 AI 走同一条授权管道"的架构兑现，也是冷启动流量（人类日常申请）与未来 Agent 流量共存的基础。

## 6. 与现有引擎的接缝清单

| 复用点 | 用途 | 改动 |
|---|---|---|
| `ProcessEngine.execute` 命令管线+乐观锁 | 所有写操作网关侧照走（NFR 一致性） | 无 |
| `RuntimeService.start_instance` | approval_chain 编译实例的启动 | 传参扩展（注入 proposed_by_agent 变量） |
| `TaskService` 七类操作 | approve/reject/delegate 映射到既有任务操作 | 无或薄适配 |
| `HistoryService`（只追加） | 证据链底座 | 扩展查询字段（policy_version_id） |
| `Jobs` + CAS | SLA 超时升级 | 超时动作从"仅记事件"扩为"升级参与者+通知" |
| `EngineConfig.notifier`（noop→实现） | 卡片/webhook 投递 | SPI 已留，实现 notifier 模块 |
| definitions 层 diff/发布范式 | 策略版本化交互 | 模式复用，不共享表 |
| OrgDirectory SPI | 审批人解析（角色/主管） | authorization/directory 提供默认实现 |
| 定义层流程（报销等模板） | 人侧申请的流程载体（直接启动实例，无需策略编译） | 新增 application_type 引用 |

## 7. 安全设计要点

1. agent 凭证：`token_hash`（Argon2）存储；泄漏可即时吊销（suspended 即拒）。
2. MCP/REST 统一鉴权中间件；`acted_as_agent` 与 `acted_by` 在 audit_event 强制非空（迁移校验）。
3. 卡片回调验签（钉钉/飞书签名规范）+ 重放窗口。
4. payload 中敏感字段（手机号等）在卡片摘要里脱敏展示（完整值仅审计库）。
5. deny-by-default：未知动作一律拒绝并提示管理员配置策略。
