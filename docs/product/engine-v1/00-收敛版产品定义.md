# flowork 流程引擎 v1 · 收敛版产品定义

> 2026-10-03 收敛决策。**本文取代 `agent-gateway-v1/` 四篇作为 v1 范围权威**（那份 PRD 的元素按下文处置表分流，其用户故事与原型仍有效作为素材与愿景演示）。终局愿景不变（docs_research/flowork最终形态-组织授权层-2026-10.md），本文只是把它落成"先卖引擎、再长授权层"的顺序。

## 1. 收敛后的一句话

**一个可独立部署的流程引擎：内置组织身份与权限，REST + MCP 双开放——第三方应用和 AI Agent 都能在上面发起、构建、办理传统审批流。**

四个产品支柱：

1. **引擎**（已有，M0–M6 完结）：durable 审批语义——会签/驳回/超时升级/只追加历史/actor 归因。
2. **目录**（新增，解决问题①）：组织架构、角色、用户、Agent 的统一身份模型与映射——这是"开放给第三方"的地基。
3. **权限**（新增，解决问题②）：凭证 + 作用域 + RBAC + 资源可见性，覆盖人、Agent、第三方应用三类调用方。
4. **开放面与部署**（新增）：REST 全量 API、MCP 薄工具面、docker 一条命令自托管。

产品文档全套：[01-身份与组织模型](01-身份与组织模型.md)（问题①方案）、[02-权限模型](02-权限模型.md)（问题②方案）、[03-用户故事](03-用户故事.md)（角色/史诗/验收标准）、[04-需求规格](04-需求规格.md)（FR 详细规格+追踪矩阵；本文 §3 是其摘要）、[05-架构总体设计](05-架构总体设计.md)（三面同构/模块拓扑/部署）、[06-可视化配置设计](06-可视化配置设计.md)（Console）、[07-Skill与CLI生成通道设计](07-Skill与CLI生成通道设计.md)（配置即代码）、[08-日志审计与可观测性设计](08-日志审计与可观测性设计.md)（三层审计+hash chain）、[09-企业级能力清单与排期](09-企业级能力清单与排期.md)（调研基准与 v1/v1.1/v2 分层）、[10-数据能力决策](10-数据能力决策.md)（L1 数据契约进 v1/L2 按信号/L3 走生态；三类数据纪律）。

## 2. 收敛处置表（旧 PRD → 新去处）

| 原「审批网关 v1」元素 | 收敛后去处 | 理由 |
|---|---|---|
| 引擎核心/任务操作/超时升级/审计底座 | **v1 核心，不变** | 已建成，236 测试 |
| MCP 接入（US-101~105） | **v1 保留**，工具面从"审批网关语义"改为"引擎语义"（start_flow/get_instance/…） | 引擎即产品，MCP 是开放面之一 |
| 组织目录（原 v1.1 对接企业目录） | **提前进 v1，升为支柱** | 用户点名的两个问题之一；没有它 API 无法开放 |
| 权限（原只有 NFR-03 一句话） | **提前进 v1，升为支柱** | 同上 |
| Agent 注册/停用（US-301） | **v1 并入目录**：Agent 是目录里的一等身份 | 与用户/角色同一模型管理 |
| 人发起申请（E6 报销） | **v1 即"传统审批流"本身**：设计器构建 + API/UI 发起 | 收敛后不需要单独"申请中心"概念 |
| 极简任务页（原收件箱降级版） | **v1 保留**：开箱演示与兜底办件入口 | 引擎可无 UI，但独立部署要能立刻跑通 |
| IM 审批卡片（钉钉/飞书） | **v1.1**；v1 只做 webhook 通知（Notifier SPI 已留） | 卡片适配是渠道工程，不阻塞核心 |
| 风险策略/信任档/自动通过/上岗证 | **上移 v2「授权层」模块**；v1 数据模型只留 `policy hook` 扩展位 | 这是有差异化的上层，但必须长在引擎地基上 |
| 控制台四视图（原型） | **v1.x 起逐步**（名册并入目录管理页）；原型继续做愿景演示 | 引擎优先，控制台是引擎的壳 |
| 审计导出/CS108 报告 | v1 保留 audit 只读 API；报告 v1.1 | API 优先 |

## 3. 收敛后 FR 清单（摘要；详细规格与 US 追踪见 [04-需求规格](04-需求规格.md)）

### 3.1 目录（DIR，详见 01 文档）

| ID | 需求 | 优先级 |
|---|---|---|
| DIR-01 | OrgUnit 树 / User / Role（范围化）/ RoleAssignment 的 REST CRUD 与 CSV 批量导入 | P0 |
| DIR-02 | Agent 一等身份：注册、负责人、所属部门、可选"代表某人"（on_behalf_of）、一次性凭证、停用即时生效 | P0 |
| DIR-03 | 实现 OrgDirectory SPI：`manager_of` / `dept_head` / `users_with_role(role, scope)`，接通既有参与者函数（originator/manager/manager_of/dept_head/users_with_role/委托替换） | P0 |
| DIR-04 | 同步源策略：内置目录为事实源，v1.1 增钉钉/飞书/LDAP 拉取同步（SPI 已隔离） | P1 |

### 3.2 权限（PERM，详见 02 文档）

| ID | 需求 | 优先级 |
|---|---|---|
| PERM-01 | 三类凭证统一：user token / agent credential / 第三方 api_key；哈希存储、可吊销 | P0 |
| PERM-02 | Scope 作用域控制 API 可调面（definitions:write / instances:start / tasks:act / audit:read / directory:* …） | P0 |
| PERM-03 | 平台角色 RBAC：admin / designer / operator / auditor / member，REST 与 MCP 共用同一中间件 | P0 |
| PERM-04 | 资源可见性：任务只办自己的（引擎参与者路由）；实例发起人+参与人+auditor 可读；定义可配"允许发起"名单 | P0 |
| PERM-05 | 第三方应用代表用户发起：`on_behalf_of` 归因（审计落到人，应用留痕） | P0 |

### 3.3 运行时开放面（RUN）

| ID | 需求 | 优先级 |
|---|---|---|
| RUN-01 | 实例 API：发起（幂等键）、查询状态/当前步骤/等待人、历史、等待（长轮询） | P0 |
| RUN-02 | 任务 API：我的待办、complete/reject（意见必填）/delegate/转办 | P0 |
| RUN-03 | 定义 API：沿用现有设计器 REST（CRUD/publish/validate/dry-run/diff），挂权限 | P0（已建） |
| RUN-04 | MCP server：8 工具薄面（见 01 文档 §6），stdio+HTTP | P0 |
| RUN-05 | webhook 终态通知（HMAC 签名重试） | P1 |
| RUN-06 | 极简任务页（登录→待办列表→办件，服务端渲染即可） | P1 |

### 3.4 运维（OPS）

OPS-01 docker compose 一键部署（engine+api+worker+SQLite/Postgres）P0；OPS-02 /health+指标 P1；OPS-03 多副本文档（Job CAS 已保证）P1。

## 4. 与现有资产的映射（收敛的工程红利）

```
已有（直接复用）                    新增（v1 全部工作量）
─────────────────────              ─────────────────────
flowork 引擎 M0–M6 全量语义         flowork/directory/   目录+SPI实现（DIR）
designer/ 前端 + 定义 REST          flowork/auth/        凭证+scope+RBAC（PERM）
flowork/spi/ports.OrgDirectory      flowork/runtime_api/ 实例/任务 REST（RUN-01/02）
flowork/participants/ 参与者函数     flowork/mcp/         MCP server（RUN-04）
Jobs CAS 超时 / outbox 审计底座     web 任务页 + docker 打包（RUN-06/OPS）
```

参与者解析的现状特别值得说明：`functions.py` 已内置 originator / manager / manager_of / dept_head / users_with_role 与委托替换，`resolver.py` 已有 fallback——**组织映射是"给 OrgDirectory 一个真实实现"的填空题，不是新建题**。

## 5. 里程碑（单人×AI 节奏）

- **M-A 目录与权限（3–4 周）**：DIR-01~03 + PERM-01~04，测试先行（AGENTS.md 四道门）。
- **M-B 开放面（2–3 周）**：RUN-01/02/04，MCP 工具面 + 幂等 + 长轮询等待。
- **M-C 可交付（1–2 周）**：任务页、docker、webhook、文档（接入指南 + 10 分钟 quickstart）。
- v1 发布故事：「自托管审批引擎 + 让你的 Agent 进审批链」；v2 才讲「授权层/上岗证」。

## 6. 风险

| 风险 | 缓解 |
|---|---|
| 目录做成小 HR 系统（蔓延） | v1 字段刻意贫瘠：部门树+主属+主管+角色，岗位/兼岗/代理人进 backlog（01 §7） |
| 权限模型过度设计（ABAC/租户） | v1 三层封顶；资源可见性只有四条规则；多租户进 v2 |
| MCP 工具面漂移成全量 API | 工具面固定清单，写进 01 §6 的"纪律"段（首发 8 个；2026-10-08 经 kernel-v2 §13 扩展为 18 个，见 01 §6 注） |
| v2 授权层被砍后叙事断裂 | policy hook 扩展位 + 终局文档仍在；引擎客户就是授权层未来客户 |
