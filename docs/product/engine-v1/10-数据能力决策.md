# flowork 引擎 v1 · 数据能力决策

> 2026-10-03 决策记录。问题：流程引擎是否应具备数据建模能力？结论：**引擎需要的是对数据的"契约"，不是对数据的"持有与管理"**。本文定档位、立纪律、给升级信号；规格落点在 [04 §2.3 DEF 组](04-需求规格.md)，生成通道落点在 [07](07-Skill与CLI生成通道设计.md)。

## 1. 决策

| 档位 | 决策 | 时机 |
|---|---|---|
| L1 数据契约（business_object） | **做，升格进 v1**（原 DEF-02 加强） | v1（M-B 随定义管线） |
| L2 轻实体存储（单表物化+CRUD+列表页） | 预留设计，按成单信号启动 | v1.1 |
| L3 数据建模平台（实体/关系/字段权限/join） | **不自建**：走 BYO-data SPI 或生态集成 | v2+ |

## 2. 四档位与业界参照

| 档位 | 能力 | 代表 | 数据放哪 |
|---|---|---|---|
| L0 | 无结构变量 dict | 早期 BPM | 调用方系统 |
| L1 | 类型化 schema/校验/版本化 | Camunda 8、Temporal（近似） | 调用方系统 |
| L2 | 单表物化 + 自动 CRUD + 列表页 | Flowable、Bonita 业务数据 | 引擎内 |
| L3 | 数据建模平台 | 对标产品、NocoBase、简道云 | 引擎即数据源 |

不做 L3 的三个理由：工程量是另一个产品（NocoBase 的全部）；API-first 引擎的核心客户（第三方应用/集成商）自带数据库，Camunda 模式已被验证；半吊子 schema 系统会毒化 API，第三方围绕残缺模型写代码后无法收回。

## 3. 三类数据纪律（防蔓延的边界，评审依据）

| 类 | 例 | 引擎的姿势 |
|---|---|---|
| 流程控制数据 | 路由条件用的变量 | 引擎自己的，L1 契约管 |
| 业务单据数据 | 报销金额、行项、附件 | L1 契约管结构；存储可选（v1 随实例 JSON 落库） |
| 主数据/引用数据 | 客户、供应商、物料档案 | **永远是别人的**：只存 ID 引用 + 展示快照，绝不复制同步成"顺手建表" |

## 4. L1 规格：业务对象（business_object）

**资产定义**（三面同构，走同一 draft→validate→diff→publish 管线）：

```yaml
# business_objects/expense.yaml
code: expense
name: 报销单
version: 3
fields:
  - {name: amount,  type: amount,  required: true, constraint: {min: 0}}   # 金额：带量纲，路由条件一等公民
  - {name: reason,  type: text,    required: true, max_length: 200}
  - {name: category,type: enum,    required: true, values: [差旅, 业务招待, 办公]}
  - {name: occurred_at, type: date, required: true}
  - {name: attachments, type: attachment, multiple: true}                  # 仅元数据（id/name/size/url），字节流不入引擎
  - {name: customer,  type: ref, entity: crm.customer}                     # 主数据引用：{id, display_name}
```

**类型系统（v1 封闭集）**：text / number / amount / date / datetime / enum / bool / attachment(元数据) / ref / json（逃生舱，仅显式声明处可用）。

**四条关键语义**：

1. **版本不可变 + 发布钉住**：定义发布时钉住 `bo@version`，在途实例按旧版解释——与定义快照隔离同构（DEF-05）。
2. **展示快照（审计保真）**：ref 字段在提交时冻结 `{id, display_name}`——**审计回放显示的是审批人当时看到的名称**，主数据后来改名不影响历史（DEF-08）。
3. **三处消费**：任务页按 schema 渲染单据详情（字段中文名/格式化/附件链接，DEF-07）；`fw_get_flow` 返回引用的 bo schema，agent zero-shot 填参（RUN-06 强化）；审计 detail 结构化展示（AUD-01 强化）。
4. **校验前移**：发起 payload 全类型校验（枚举/约束/必填），422 错误定位到字段路径（DEF-06）——路由条件（金额>1万）因此建立在类型与量纲可靠的地基上。

## 5. L2 预留与启动信号（v1.1）

设计预留：business_object 物化为 business_record（单表、文档式、可索引字段白名单、**不做 join**）+ 自动 CRUD API + Console 列表页；字段级权限矩阵（对标产品差距清单项）进 v2。

启动信号（出现两次即做）：成单沟通中客户问"**审批的数据最后存在哪、我们自己怎么查**"——说明客户没有应用开发团队，单据数据需要落点。文件字节存储同桶决策（FileStore SPI）。

## 6. L3 路线（v2+，不自建）

两条优先于自建的路：①**BYO-data SPI**——业务对象映射到客户已有库表/视图（只读引用 + 校验），引擎保持无状态；②**生态集成**——与 NocoBase 这类"数据建模为体、流程为插件"的产品互为集成（我们是镜像：流程为体、数据为契约），让它们集成我们比自己长成它们便宜一个数量级。

## 7. 风险

| 风险 | 缓解 |
|---|---|
| schema 演进破坏在途实例 | 发布钉住 + 旧版解释（同定义快照）；diff 视图高亮字段级变更 |
| json 逃生舱被滥用 | 仅显式声明字段可用；Console/skill 均不鼓励；审计对 json 字段打标 |
| L2 信号误判（把"想导出报表"当"要存储"） | 信号问句锁定"自己怎么查单据"；报表需求先走审计导出（AUD-03） |
| 附件元数据与真实文件漂移 | v1 display 存 URL+哈希摘要；FileStore 决策时一并处理 |
