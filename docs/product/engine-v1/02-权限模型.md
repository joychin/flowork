# flowork 引擎 v1 · 权限模型（问题②方案）

> 解决：**权限**。核心设计判断先行：这里有两个经常被混为一谈的权限世界，必须先分开再分别建模——
> **平台权限**（你能不能调这个 API/看这份数据）与**流程权限**（这个任务轮不轮到你办）。
> 流程权限不是权限系统的职责，它是[组织模型](01-身份与组织模型.md)参与者解析的输出；权限系统只管平台侧。

## 1. 三层模型总览

```
L1 凭证层（你是谁）        L2 作用域层（你能调什么）         L3 资源层（你能看/动哪些）
────────────────         ──────────────────────          ──────────────────────
user token               scopes（细粒度能力）              任务：只办自己的（引擎路由）
agent credential    ───▶  + 平台角色 RBAC（能力打包） ───▶  实例：发起人+参与人+audit可读
api_key(第三方应用)        admin/designer/operator/        定义：可选"允许发起"名单
                          auditor/member                  目录：directory:* 控制
```

## 2. L1 凭证：三类调用方统一为 principal

| 凭证类型 | 绑定的 principal | 典型持有者 | 说明 |
|---|---|---|---|
| `user_token` | user | 管理员/审批人/设计者 | 任务页登录或 CLI 换取 |
| `agent_credential` | agent | AI Agent（Claude/自研/悟空 skill） | 一次性明文，哈希存储；随 agent 停用即时失效 |
| `api_key` | application（虚拟 principal，可选绑平台角色） | 第三方报销应用/ERP/低代码平台 | **代表用户发起必须带 `on_behalf_of`**（PERM-05），审计归因到人 |

统一规则：所有凭证 = `(credential_id, secret_hash, principal_kind, principal_id, scopes[], status, expires_at?)`；吊销即时生效（每请求校验 status）；签发/吊销本身进审计事件。

## 3. L2 作用域与平台角色

**Scope 清单（v1 封闭集合，代码里枚举）**：

| 组 | scope |
|---|---|
| 定义 | `definitions:read` `definitions:write`（含 publish/validate/dry-run/diff） |
| 实例 | `instances:start` `instances:read` `instances:admin`（暂停/恢复/终止） `instances:variables`（外部改实例变量值，PATCH /v2/instances/{id}/variables；读变量沿用实例可见性规则，不另设 scope） |
| 任务 | `tasks:read` `tasks:act` |
| 目录 | `directory:read` `directory:write` |
| 审计 | `audit:read` |
| 系统 | `credentials:admin`（发/吊凭证） |

**平台角色（scope 的打包，绑给 user 与 api_key）**：

| 角色 | scope 包 | 对应人 |
|---|---|---|
| admin | 全部 | 林姐（也承接流程兜底 to_admins 的 admins 定义） |
| designer | definitions:* + instances:read + directory:read | 流程管理员 |
| operator | instances:admin + tasks:read + audit:read | 运维（暂停/转办） |
| auditor | instances:read + tasks:read + audit:read | 何敏 |
| member | instances:start + tasks:read/act + definitions:read | 所有人默认 |

中间件一处实现、两处挂载：REST（FastAPI dependency）与 MCP server（握手后注入）走同一鉴权管线——**MCP 不是权限旁路**。

## 4. L3 资源可见性（v1 只有四条规则）

1. **任务**：act 仅限 assignee/candidate（引擎参与者路由的结果）；read 自己的+被抄送的。
2. **实例**：read = 发起人 ∪ 历史参与人 ∪ 持 `instances:read`；列表接口按此过滤（v1 不做部门范围可见，进 backlog）。
3. **定义**：`definitions:read` 全可见；**发起控制** = `instances:start` 为默认许可，定义可配 `restricted_start: [principal…]` 白名单（如"财务专用流程"只允许财务角色/api_key 指定应用发起）。
4. **目录**：全员 `directory:read`（审批要解析人名）；写仅 `directory:write`。

第三方应用代表语义（PERM-05）：api_key 发起实例时必须携带 `on_behalf_of(user)`；落库 `started_by=该用户`、`via_application=api_key`——**问责到人、留痕到应用**，审计双归因。缺 on_behalf_of 则实例归属应用自身 principal（仅限无人格场景，默认关闭）。

## 5. 典型走查（模型自检）

| 场景 | 凭证 | 判定路径 |
|---|---|---|
| Claude 想发起"设备采购"审批 | agent_credential | L1=agent → L2 scopes 含 instances:start → L3 定义无 restricted_start → 放行；started_by=agent（+on_behalf_of 若配） |
| 第三方报销应用替小陈提交 | api_key + on_behalf_of=小陈 | L1=application → L2 instances:start → L3 放行；归因 started_by=小陈, via=app |
| 老周经 MCP 办任务 | user_token | fw_complete_task → L2 tasks:act → L3 该 task 的 assignee=老周 → 放行；他人任务 404（不 403，避免探测） |
| 何敏导出全部审计 | user_token(auditor) | L2 audit:read → L3 实例可见性对持 audit:read 放开 → 放行 |
| suspended agent 调 fw_start_flow | agent_credential | L1 status 校验即拒（先于 L2），错误信息指向注册指引 |
| 应用想改流程定义 | api_key（无 definitions:write） | L2 即拒——定义变更永远走设计器+人的审批 |

## 6. 安全要点

1. 凭证哈希（Argon2）存储，明文仅签发时一次；`credentials:admin` 单列（发凭证的权限不等于 admin）。
2. 最小 scope 发放：签发界面按角色模板+手工增删，默认 member 包。
3. 所有鉴权失败/成功进结构化日志（principal、scope、资源、request_id 贯穿）。
4. 404 优先于 403（不可见资源不暴露存在性）。
5. 引擎侧不变量继续成立：一切写操作带 actor 归因（凭证→principal 是 acted_by 的来源）。

## 7. v2 授权层的挂点（刻意预留，不在 v1 实现）

- `agent.trust_tier / quota` 字段位、`policy_version` 表、动作风险规则 → 收敛版 00 文档处置表已声明上移 v2。
- SoD（角色互斥）进 L2/L3 之间（v2）：`role` 表加 `conflicts_with`。
- 多租户：L3 之上加 tenant 维度，凭证带 tenant_id——引擎数据模型现在就用 `namespace` 字段占位（定义已支持），避免 v2 迁移伤筋动骨。

## 8. 开放问题（backlog）

scope 是否需要租户/环境维度（v2）；`instances:admin` 是否细分（暂停 vs 终止 vs 迁移）；目录写的审批化（改组织也走一条流程——自举，很酷但 v1 不做）；API key 轮换策略。
