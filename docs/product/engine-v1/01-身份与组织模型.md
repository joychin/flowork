# flowork 引擎 v1 · 身份与组织模型（问题①方案）

> 解决：**组织架构、角色、用户、Agent 的映射**。原则：目录是引擎的"事实源"模块（独立部署不依赖外部系统），但经 SPI 允许被企业真实目录覆盖/同步。

## 1. 现状与填空点

引擎已预留（`flowork/spi/ports.py` + `flowork/participants/`）：

```python
class OrgDirectory(Protocol):
    def manager_of(self, user_id: str) -> str | None: ...
    def users_with_role(self, role: str) -> list[str]: ...
```

参与者函数已内置：`originator / manager / manager_of / dept_head / users_with_role` + 委托替换（`resolve_with_delegation`）+ 无参与者兜底（`fallback_when_empty`）。

**v1 的活**：①给 OrgDirectory 一个持久化实现（新建 `flowork/directory/`）；②Protocol 扩两个签名（角色范围化、Agent 问责）；③Agent 进目录成一等身份。

## 2. 统一身份模型

```
OrgUnit（部门树）                 User（用户）
  org_unit_id, parent_id,          user_id, name, email,
  name, path,                      org_unit_id（主属）, status
  manager_user_id（部门主管）
                Role（角色，范围化）
                  role_code, name,
                  scope: global | org_unit_id
                        RoleAssignment（授权）
                          user_id, role_code, org_unit_id?

Agent（AI 身份，一等 principal）
  agent_id, name,
  owner_user_id（负责人：升级与问责的责任人）
  org_unit_id（所属部门：统计与升级路径归属）
  on_behalf_of_user?（可选：代表某用户行动，审批界面显示"AI 代 张三"）
  status: trial | active | suspended
```

**关键语义（映射的根，写死不许含糊）**：

| 语义 | 规则 | 被谁消费 |
|---|---|---|
| "某人的直接主管" | 主属部门的 `manager_user_id`（部门属性，**不是**角色） | `manager_of()` → 参与者函数 `manager` |
| "某部门主管" | 该 OrgUnit 的 `manager_user_id` | `dept_head()` |
| "找财务" | `RoleAssignment(role=finance, scope 覆盖发起人部门)`；部门无命中则沿树向上找最近命中（范围解析规则） | `users_with_role(role, scope)` → 会签 |
| "Agent 出事找谁" | `owner_user_id`；升级链：agent owner → 所属部门主管 → 上级 | 审计/超时升级（v2 策略层也用） |
| "AI 代某人提交" | `on_behalf_of_user` 存在时，`submitted_by` 归因到该用户，`acted_as_agent` 附注 | 发起 API 与审计 |
| 停用 | agent suspended → 新请求拒绝、在途按无参与者兜底策略处理（现有 fallback_when_empty 直接复用） | 引擎 |

范围解析规则细节（`users_with_role` 的 scope 匹配）：角色授权时指定了 org_unit 则只在该子树生效；未指定则全局。查找顺序：发起人所在部门子树 → 逐级向上 → 全局授权。命中多人为会签语义（由流程定义的会签出口决定，目录只给人）。

## 3. 表结构（新增 `flowork/directory/`）

| 表 | 字段 | 说明 |
|---|---|---|
| `org_unit` | id, parent_id, name, path, manager_user_id | 树，path 便于子树查询 |
| `user` | id, name, email, org_unit_id, status | v1 单主属部门 |
| `role` | code, name, scope_type(global/org_unit), scope_org_unit_id? | 角色本身可带默认范围 |
| `role_assignment` | id, user_id, role_code, org_unit_id? | 授权行（覆盖/收窄角色默认范围） |
| `agent` | id, name, owner_user_id, org_unit_id, on_behalf_of_user?, status, created_at | 上岗证的最小形态（v2 策略层在此之上加信任档/额度） |
| `agent_credential` | agent_id, token_hash, issued_at, revoked_at | 与 PERM 的凭证表同族（见 02 §2） |

**OrgDirectory 实现要点**：全部方法纯读、带内存缓存（目录变更频率极低，实例推进不回源查库）；`users_with_role` 的范围解析在 SQL 层完成（path 前缀匹配 + 逐级向上）。

Protocol 扩展（向后兼容，带默认实现）：

```python
class OrgDirectory(Protocol):
    def manager_of(self, user_id: str) -> str | None: ...
    def users_with_role(self, role: str, *, within: str | None = None) -> list[str]: ...  # +范围
    def agent_owner(self, agent_id: str) -> str | None: ...                               # +问责
```

## 4. 目录数据从哪来（三级策略）

1. **内置（v1）**：REST CRUD + CSV 批量导入（部门/用户/角色授权三张表各一个模板）。独立部署 10 分钟搭出可用目录——这是"引擎可独立交付"的底线。
2. **同步（v1.1）**：钉钉/飞书/LDAP 拉取同步（增量定时任务），同步是内置目录的一个"写入方"，不绕过事实源；冲突策略：远端优先、本地手工行加保护标记。
3. **接管（v2，可选）**：`DelegatingOrgDirectory`——读操作直接代理企业目录（每次解析走远端+缓存），适合不肯落库的客户。SPI 边界已支持这种插拔。

## 5. 与既有引擎的接缝

| 既有件 | 接法 |
|---|---|
| `ParticipantFunctions` 注册表 | 目录实现就位后，`manager/dept_head/users_with_role` 从"需要注入 org 才能用"变为默认可用 |
| `resolve_with_delegation`（委托替换） | 委托关系表（user→delegate，v1.1）进目录；v1 先支持审批链里显式 `delegate` 操作产生的临时委托 |
| `fallback_when_empty`（无参与者兜底） | 现有 raise/to_admins 两档；"to_admins" 的 admins 定义进权限模型的平台角色（见 02 §3） |
| 实例发起归因 | `start_instance(started_by=principal)`：principal 为 user 或 agent（+on_behalf_of），落 `acted_by/acted_as_agent` 双链 |

## 6. MCP 工具面（引擎语义，收敛版）

| 工具 | 参数 | 返回 | 谁用 |
|---|---|---|---|
| `fw_list_flows` | — | 可发起的定义列表（code/名称/变量 schema 摘要） | agent/应用 |
| `fw_get_flow` | code | 变量 schema、路由预览（复用 dry-run） | agent |
| `fw_start_flow` | code, variables, idempotency_key, on_behalf_of? | instance_id, 当前步骤, 等待人 | agent/应用 |
| `fw_get_instance` | instance_id | 状态/当前步骤/等待人/历史摘要 | 发起方 |
| `fw_wait_instance` | instance_id, timeout_seconds | 终态或"下一人工步骤"变化 | 发起方（长轮询） |
| `fw_my_tasks` | status? | 我的待办（含 on_behalf_of 的） | 人（经 MCP 客户端） |
| `fw_complete_task` | task_id, action(approve/reject), comment | 新状态 | 人 |
| `fw_delegate_task` | task_id, to_user | 新办理人 | 人 |

**纪律**：固定 8 个。定义的增删改不上 MCP（走设计器/REST，那是人的工作）；引擎高级操作（暂停/恢复/迁移）不上 MCP（operator 经 REST）。工具描述里写清幂等键与超时语义，token 预算友好。

## 7. 开放问题（记 backlog，不进 v1）

一人多部门（兼岗）与按场景切换主属；岗位（position）维度；代理人（vacation delegation）常设规则；角色互斥（SoD，财务与出纳不得同人——v2 权限层的好料）；部门副主管与多主管。
