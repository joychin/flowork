# flowork 引擎 v1 · 设计器能力补全规划

> 2026-10-09 规划稿，状态：**批 A–D 已落地（同日，含用户追加的连线改接重做与右键菜单）；批 E/F 核心已落地（词汇下发+点选、定义/节点下拉），handler 名录与批 G（模拟试跑）仍待拍板**。落地明细见 designer/README 与 git log（feat(designer)/feat(web) 批次提交）。核查方式＝逐文件读码 + 真实界面走查（浏览器实跑用户本地 dev server）+ 引擎行为实测（同一份定义喂给 `simulate_route`）。改动范围：节点注册表的 `ui` 元数据、`/api/*` 传输面、设计时工具（`dry_run` 模拟面）与 `designer/` 前端——**不触碰运行时语义与数据模型**。
> 与 [06 可视化配置设计](06-可视化配置设计.md) 的关系：06 定义"关键功能可视化覆盖清单"与 Console 信息架构，本文是其中「流程定义（设计/校验/dry-run/diff/发布）」一块的**落地缺口清单与补全排期**。

## 0. 一页结论

用户反馈「设计器好像缺失等待节点、子流程」。核查结论：**这两个节点并没有缺席**——它们已在引擎注册、已随 `/api/node-kinds` 下发、已出现在设计器左侧调色板（截图实证：「事件」组下有「等待消息」「延时等待」，「自动化」组下有「子流程」）。真正的问题是**配置、验证、表达三层断点**，叠加起来的观感就是"这个功能不存在"：

| 断点 | 典型症状 | 影响 |
|---|---|---|
| ① 配不了 | 审批节点的多级超时 `deadlines` 被渲染成字符串标签框，填进去只会得到 `[object Object]`；流程级三块配置（入参契约、实例时限、消息启动）在界面上完全没有入口 | 用户被迫直接改 Spec JSON，可视化承诺落空 |
| ② 看不懂 | 等待节点的表单里出现裸英文标题 `WaitMessage`；子流程的 `binding`、`multi_instance` 掉进"其他"组且无中文标签；等待节点在调色板上没有图标 | 用户不知道该填什么，误以为功能缺失 |
| ③ 验不了 | 任何含等待节点的流程，「试运行」必然报"流程在此无法路由"（`wait.*` 未注入模拟上下文）——这是最致命的一条：试运行是设计器最重要的验证工具，等待节点在它面前等于坏的 | 用户按"试运行"→ 报错 → 断定等待节点不能用 |
| ④ 没辅助 | 条件公式只有一句 `initiator` 提示；变量选择器不存在（但界面文案声称"连线条件可直接点选变量"）；子流程的 `process_code`、审批节点的 `reject_target` 都是裸文本框；消息名、handler 名无从查 | 拼写错误只能靠校验兜底，编辑体验差 |

## 1. 现状证据（核查记录）

### 1.1 后端链路是通的

`GET /api/node-kinds` 返回全部 8 种内置节点，每项含 `ui`（中文名 / 图标 / 调色板预设 / 表单分组）与完整 JSON Schema：

```
kinds: start, end, branch, user_task, service_task, call_activity, cc_task, wait
wait  ui = {name: 等待, icon: clock, palette: [等待消息, 延时等待], form_groups: [基础, 时间]}
call  ui = {name: 子流程, icon: box, palette: [子流程], form_groups: [基础, 子流程, 数据映射]}
```

所以「缺失」不在链路，在下面三节的呈现与交互。

### 1.3 三条实测记录

**（一）试运行对等待节点必然失败。** 造一份最小定义（开始 → 等待"回款到账"超时 1440 分钟 → `wait.result == "matched"` 走"到账" / `== "elapsed"` 走"超时"），喂给 `simulate_route`：

```
ok: False
warnings: 条件求值失败（… undeclared reference to 'wait' …），按不满足处理
blocked: ['节点 wait 的出边条件全部不满足且无默认边，流程在此无法路由']
```

原因在 `flowork/definitions/dry_run.py`：模拟上下文只注入样例变量 + `initiator` / `now` / `instance` 三个占位，`wait.*`（以及 `prev_task`、`task.*`）没有占位假设，于是等待节点的分派条件必定求值失败。**任何使用等待节点的流程，在界面上都无法试运行。**

**（二）`deadlines` 在界面上不可配置。** `designer/src/components/SchemaForm.tsx` 对 `type: "array"` 无差别走标签输入分支（`(value as unknown[]).map(String)`）。`deadlines` 是对象数组（`items: $ref TaskDeadline`），一旦有值就显示 `[object Object]`，且没有任何增删条目的入口。v2.2 把多级超时从 `timeout` 升级为 `deadlines` 列表，界面只跟上了旧形态。

**（三）嵌套对象的标题与字段标签没有中文通路。** 属性面板的分组与标签来自三处：registry 的 `form_groups`、前端的 `FIELD_LABELS` 全局小表、pydantic 导出的 `title`。嵌套模型（`WaitMessage` / `CallInstanceConfig` / `TaskDeadline` / `MultiInstance`）的 `title` 是**类名**，前端无 `WaitMessage → 等待消息` 的映射；且 `FIELD_LABELS` 按字段名扁平匹配，`WaitMessage.name` 与节点自己的 `name` 撞名，错显为「节点名称」。

### 1.4 其余核查发现

- **部署期校验在设计期看不到**：`/api/validate` 只跑设计时校验；L3/L4（handler 未注册、`binding=deployment` 的目标未发布、取人位目录实体不存在）只在发布（deploy）时执行。用户点「发布」才第一次看到这些问题。
- **模拟试跑（A10）无入口**：内核已有 `RuntimeService.simulate`（模拟实例试跑，返回终态 / 令牌时间线 / stub 清单 / 卡点 / 路由轨迹），web 无端点、设计器无按钮。
- **词汇目录已在公开 API 就绪**：`identifier_entries` / `engine_functions` / `reserved_identifiers` 均已从 `flowork.api` 导出，只差一个下发端点与前端消费（即 expression-dataface 计划的 F4）。
- **画布表达**：等待节点与普通任务节点在画布上完全同形（只有 `branch` 有 ?/≡ 徽章）；`Icon` 组件没有 `clock` 分支（`wait.ui.icon = "clock"` 落在 `default: return null`），调色板与画布上等待节点是**无图标**的。
- **前端文案失实**：流程设置面板写"声明后：连线条件可直接点选变量"——变量选择器并不存在（单轨化改造时移除，文案未同步）。
- **前端无自动化测试**：`designer/package.json` 没有测试脚本与测试依赖，全部靠手工浏览器走查；`RightPanel.tsx`（500 行）、`Canvas.tsx`（594 行）、`store.ts`（594 行）已超出仓库「单文件 ≤ 300 行」的惯例（该红线目前只由 Python 测试守卫，前端未覆盖）。
- **本次核查未覆盖的范围**（诚实边界）：`/api/definitions/{code}/diff` 与发布对话框、`DesignerList` 列表页、`ConnectMenu` 快捷新建未逐项走查——它们本次未发现与等待节点/子流程相关的问题，但也没有得到同等强度的证据。批 A 引入组件测试后可把这些纳入回归网。

## 2. 缺口清单（按用户价值排序，G 编号供后续引用）

### 组 A：配置能力（P0，决定"能不能用"）

| 编号 | 缺口 | 说明 |
|---|---|---|
| G-A1 | 对象数组无编辑器 | `deadlines` 等"列表套对象"字段需要可增删的重复子表单；这是 SchemaForm 的能力缺口，补一次通用于全部现有与未来字段 |
| G-A2 | 流程级三块配置无入口 | 入参契约 `input`、实例时限 `deadline`、消息启动 `start_on_message`——三者都已是 `ProcessDefinition` 的一等字段、`PUT` 直接落库，纯前端工作 |
| G-A3 | 自由字符串冒充枚举 | `no_participant_policy`、`timeout.strategy`、`output_mode` 在 schema 里是 `str`，界面显示文本框；建议内核收紧为 `Literal`（存量取值仅限既有几个，安全），前端自动获得下拉——符合"schema 驱动、前端零代码跟进" |
| G-A4 | 字段分组缺口 | `deadlines` 应归入「驳回与超时」组；`binding` / `multi_instance` 需要「子流程」「多人子流程」分组与中文标签 |

### 组 B：表达能力（P0/P1，决定"看不看得懂"）

| 编号 | 缺口 | 说明 |
|---|---|---|
| G-B1 | 嵌套模型无中文标题通路 | 建立"父对象感知"的标签解析：registry 的 `ui` 元数据增加 `field_labels`（按字段路径），前端优先取它、退到前端表、再退到 schema title。同时清理前端标签表里**已失效**的条目（`approve_exit` / `disapprove_exit` 的「比例」措辞） |
| G-B2 | 等待节点无图标 | `Icon` 组件补 `clock`（以及若干通用图标），并加"未知图标名 → 通用方框"兜底，避免未来新增节点再次无声消失 |
| G-B3 | 节点上无关键参数摘要 | 等待节点应显示"等什么/等多久"（消息名 / 超时分钟），子流程显示被调 code；现在两者与普通任务节点无法区分 |
| G-B4 | 等待节点无模式徽章 | 仿 `branch` 的 ?/≡，给等待节点加"等消息 / 延时 / 竞速"三态徽章 |

### 组 C：验证能力（P0，决定"敢不敢发布"）

| 编号 | 缺口 | 说明 |
|---|---|---|
| G-C1 | 试运行不支持等待节点 | 给 `wait.*`（以及 `prev_task` / `task.*`）提供模拟假设；见 §6 待拍板 1 |
| G-C2 | 部署期校验设计期不可见 | 让 `/api/validate` 可选带"发布口径"（跑 L3/L4 并以 WARNING 呈现），把「点发布才炸」提前到编辑期 |
| G-C3 | 模拟试跑无入口 | A10 能力（整图试跑、卡点清单）接到设计器：一个按钮跑一遍，看卡在哪 |
| G-C4 | 公式试算位点不全 | 试算与试运行同样缺 `wait.*` / `prev_task` / `task.*` 的假设；公式编辑器应知道"这个公式在哪个位点、有哪些词可用" |

### 组 D：建模辅助（P1/P2，决定"顺不顺手"）

| 编号 | 缺口 | 说明 |
|---|---|---|
| G-D1 | 词汇提示与变量点选缺失 | 条件/取人/映射编辑位应能点选变量与词汇（含中文标签、按位点过滤），即 F4 |
| G-D2 | 定义引用无下拉与下钻 | `process_code` 用已发布定义列表做下拉；点节点可跳到被调定义；反向给出"谁调用了本定义" |
| G-D3 | 节点/动作名录缺失 | `reject_target` 用本定义节点下拉；`service_task.action` 用 handler 名录下拉 |
| G-D4 | 消息名录缺失 | 配置等待节点时不知道有哪些消息名可等；见 §6 待拍板 2 |
| G-D5 | 发布管理不含回滚 | 有版本号与 diff，但没有"以历史版本为基底新建草稿"的入口 |

## 3. 分批实施计划

每批一次提交（符合仓库"每任务一提交、五道门全绿"纪律）。批 A–D 是不依赖任何产品决策的确定项；E–G 含待拍板点。

### 批 A：表单内核（G-A1 / G-A3 / G-A4 / G-B1 / G-B2）

- **范围**：SchemaForm 增加对象数组编辑器（可增删条目、每条内嵌子表单、支持必填与默认值）；建立"父对象感知"的标签解析（registry `ui.field_labels` 优先）；`builtin.py` / `wait_node.py` 补齐 `form_groups` 与 `field_labels`（`deadlines` 入「驳回与超时」，`binding` / `multi_instance` 入子流程分组）；`Icon` 补 `clock` 与未知名兜底；`no_participant_policy` / `timeout.strategy` / `output_mode` 内核 schema 收紧为 `Literal`。
- **落点**：`designer/src/components/SchemaForm.tsx`、`designer/src/components/FlowNodes.tsx`、`flowork/definitions/builtin.py`、`flowork/definitions/wait_node.py`、`flowork/definitions/node.py`、`tests/test_web_api.py`（schema 快照断言）。
- **风险与兼容**：字段收紧为 `Literal` 会让**存量定义**里该字段取其它值时加载即报错。已核实仓库内实际取值只有 `no_participant_policy ∈ {raise, to_admins}`、`TimeoutPolicy.strategy ∈ {notify, auto_approve, auto_reject}`、`output_mode ∈ {collect, merge}`，收紧安全；仓库外的数据不在承诺范围内（既有「早期零兼容」惯例）。若拍板时倾向保守，可改为保留 `str` 而在注册表 `ui.field_labels` 里给出候选值，前端渲染为可自由输入的下拉——效果相同但不影响加载校验。
- **验收**：等待节点、子流程、审批任务的**每一个** schema 字段都能在界面上用中文配置出来；含 `deadlines` 双条目的 Spec 能纯界面建成并发布；`/api/node-kinds` 快照测试锁定新的 `form_groups` 与 `field_labels`。
- **体量**：约 1.5 天。

### 批 B：流程级配置（G-A2）

- **范围**：流程设置面板（空选态）扩三块——「入参契约」（JSON Schema 编辑 + 语法校验，附"从变量声明生成骨架"捷径）、「实例时限」（开关 + 分钟数 + mark/cancel/terminate 三选一）、「消息启动」（声明列表：消息名 / 关联键 / 输入映射 / 发起人 / 业务键，支持增删条目）。
- **落点**：新文件 `designer/src/components/ProcessSettings.tsx`（从 `RightPanel.tsx` 拆出，顺带缓解 500 行超标），`RightPanel.tsx` 只留引用。
- **验收**：三块都能界面配置并发布；消息启动声明能被 `publish_message` 触发（用 CLI 或 Python API 做端到端复核）。
- **体量**：约 1 天。后端零改动。

### 批 C：试运行支持等待节点（G-C1 / G-C2）

- **范围**：`simulate_route` 接受"等待假设"（每条等待出边按假设求值：消息到达 / 超时 / 两条都试）；`/api/dry-run` 透传假设；试运行对话框加"假设"控件（默认"两条都试"，`via_reason` 标注「假设消息到达」「假设超时」）；`/api/validate` 增加 `deploy=true` 参数跑部署期校验并以 WARNING 呈现（前端在编辑期常规校验里勾选"同时检查发布项"）。
- **落点**：`flowork/definitions/dry_run.py`、`flowork/contrib/web/app.py`、`tests/definitions/test_dry_run_wait.py`（新）、`designer/src/components/DryRunDialog.tsx`。
- **验收**：§1.3（一）里的最小等待流程，试运行输出两条分支路径且不再 blocked；带 `binding=deployment` 未发布目标的定义，编辑期即见 WARNING。
- **体量**：约 1 天。

### 批 D：画布表达（G-B3 / G-B4）

- **范围**：注册表 `ui` 增加声明式徽章与摘要描述（如 `badge: {field: message, values: {…}}`），前端通用渲染；等待节点显示"等消息 / 延时 / 竞速"徽章与消息名/时长摘要；子流程节点显示被调 code；`service_task` 显示 action。
- **验收**：三种等待形态（纯消息 / 纯延时 / 竞速）在画布上一眼可辨；子流程节点无需点开即可见被调定义。
- **体量**：约 0.5 天。

### 批 E：词汇目录下发与公式辅助（G-D1 / G-C4）

- **范围**：web 增加 `GET /api/catalog`（下发 `identifier_entries` + `engine_functions` + 宿主函数签名，全部已在 `flowork.api` 导出）；条件/取人/映射编辑位旁挂词汇面板——按位点过滤、中文标签、点击插入；公式试算按位点注入 `wait.*` / `prev_task` / `task.*` 的占位假设。
- **落点**：`flowork/contrib/web/app.py`、`designer/src/components/RightPanel.tsx`（EdgeForm 等）、`designer/src/api.ts` + `types.ts`。
- **验收**：连线条件编辑器能点选出 `now` / `initiator` / `instance` / `prev_task` / `wait.result` / `node("…")` 并显示中文说明；位点不匹配的词不出现在候选里（与 validator 同源）。

## 4. 端到端验收（规划完成的判据）

在界面上从零建出这样一份流程，全程不打开 Spec JSON：

1. 开始 → **等待**（等消息"回款到账"，关联键为流程变量，超时 1440 分钟，载荷映射到 `amount`）→ 消息到达走「财务确认」/ 超时走「人工催办」两条分支；
2. 「财务确认」为**审批任务**：两级超时（24h 提醒、48h 转上级）、会签出口用公式表达、"上一步办理人自动通过"；
3. 任一步内嵌**子流程**节点，选择已发布定义、绑定方式为部署时、配置输入输出映射与多实例（按人 fan-out）；
4. **试运行**展示两条等待分支，**试跑**跑到停等卡点并给出待触发条件；
5. 流程设置里配置入参契约与实例时限；
6. 校验零 ERROR，发布成功；发布前的 diff 清单与实际改动一致。

以上六条全部达标 = 本规划落地完成。

## 5. 明确不做

- **hooks / properties 图形化**：有意留给高级用户与 Spec JSON，不进表单。
- **消息中心 / 契约库**：产品已裁定权威在生产方（flowork 只持名字 + 映射 + 入参契约消费投影），不做中心化登记。
- **表达式反解析成图形（round-trip 可视化编辑）**：既有结论不做；辅助以"点选插入 + 中文说明"为准。
- **Console 全量**（组织 / 凭证 / 任务中心 / 实例查询 / 审计）：属 06 文档的 P0/P1 另有排期，不在本规划内。
