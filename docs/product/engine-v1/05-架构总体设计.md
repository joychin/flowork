## 1. 第一架构原则：三面同构（Three Isomorphic Surfaces）

同一份配置资产，三个入口写入，**一个管线加工**：

```
 ①可视化 Console        ②REST API / MCP          ③Skill + CLI（配置即代码）
 （林姐/苏芮/老周）        （第三方应用/Agent）        （coding agent / GitOps）
        │                      │                        │
        └──────────┬───────────┴───────────┬────────────┘
                   ▼                       ▼
            ┌─────────────────────────────────────┐
            │  统一网关：鉴权(PERM) → 限流 → 审计埋点  │   ← 同一中间件，无旁路
            ├─────────────────────────────────────┤
            │  配置管线：parse → validate → dry-run  │
            │           → diff → publish(版本化)     │   ← 三面共用，产物同一
            ├─────────────────────────────────────┤
            │  应用服务：definitions / directory /    │
            │  runtime / audit 用例编排              │
            ├─────────────────────────────────────┤
            │  引擎内核（既有，零侵入）                │   ← AGENTS.md 硬约束不动
            │  registry→behavior / 路由 / tasks/jobs │
            ├─────────────────────────────────────┤
            │  支撑：persistence / clock / notifier  │
            └─────────────────────────────────────┘
```

三条推论（写进评审清单，违反即打回）：

1. **任何能力三面可达**：Console 有的配置，REST 必有对应端点，CLI 必有对应子命令——Console 永远只是 REST 的视图，不持有私有逻辑。
2. **MCP 不是旁路**：与 REST 走同一鉴权/限流/审计中间件（PERM-02）。
3. **版本化只发生一次**：publish 产出不可变版本号（定义快照隔离语义），无论从哪个面进来。目录是可变状态、走审计留痕而非版本化（与定义的区别见 07 §1）。

## 2. 模块拓扑（仓库视角）

```
flowork/
├── definitions/ runtime/ expr/ spi/ events/ errors.py     # 既有内核（不动）
├── tasks/ participants/ persistence/ engine/ jobs/        # 既有内核（不动）
├── directory/     ★ 目录：org/user/role/agent + OrgDirectory 实现（01 文档）
├── auth/          ★ 凭证/scope/RBAC + 网关中间件（02 文档）
├── runtime_api/   ★ 实例/任务 REST（RUN-01~04）
├── mcp/           ★ MCP server，8 工具冻结（01 §6）
├── console_api/   ★ 控制台后端路由组（目录/凭证/审计检索等，纯 REST 组装）
├── audit/         ★ audit_event 统一视图 + hash chain + 查询导出（08 文档）
├── assets/        ★ 配置即代码的 schema 与解析（07 文档：YAML→定义/目录装载）
├── notifier/      ★ webhook 实现（SPI 既有）；IM 渠道 v1.1
├── cli/           ★扩展：init/validate/apply/diff/publish（07 文档）
├── web/           # 既有 app.py 装配处：挂载上述路由组 + 静态托管 console/dist
└── clock.py       # 既有 naive UTC
designer/          # 既有 React18+Vite 前端 → 扩为 Console 工程的新路由区块（06 文档）
```

依赖纪律：`console_api / mcp / runtime_api / cli → assets+应用服务 → directory/auth/engine`；内核不反向依赖任何新模块；单文件 ≤300 行（AGENTS.md）。

## 3. 部署拓扑

**单机（默认交付形态）**：`docker compose up` = web(含 console 静态与调度) + worker(`flowork tick`) + SQLite 卷。10 分钟上手（US-701）。

**高可用（企业形态）**：web×n（无状态，LB 后面）+ worker×m（Job CAS 恰一次，已有）+ Postgres（主备/云托管）+ 凭证/目录读缓存一致性：目录变更经版本号失效（NFR-01）。滚动升级：先升 worker 再升 web；定义快照保证在途实例按旧版完成——**升级不中断在途审批**是引擎语义自带的（区别于需要 drain 的通用服务）。

## 4. 关键数据流

**运行流（热路径）**：`start(definition, variables, principal)` → 鉴权/scope/restricted_start → 引擎命令管线（乐观锁）→ 自动节点推进至第一个人工节点 → 任务落库+事件落 outbox（webhook 订阅方） → `wait` 长轮询挂起 → 审批人办件（三面任一）→ 推进/驳回（cause_token）→ 终态 → webhook + wait 唤醒。全程 request_id/instance_id 贯穿日志与审计（08）。

**配置流（冷路径，三面同构的落点）**：draft（Console 表单 / REST PUT / git 文件+CLI）→ validate（结构+语义+参与者可达性）→ dry-run（样例变量路由预演）→ diff（对线上版本）→ publish（版本钉住）→ 在途按旧版、新实例走新版。

## 5. 技术选型与理由

| 项 | 选型 | 理由 |
|---|---|---|
| Web 框架 | FastAPI（既有） | OpenAPI 自描述即第三方文档（NFR-07） |
| 前端 | React18+Vite（designer 既有工程扩区） | 不新开工程；设计器=Console 的一个功能区块 |
| CLI | typer（既有 5 命令扩展） | skill 通道的可执行锚点（07） |
| 存储 | SQLite→Postgres 双栈（既有） | 单机零依赖/企业 HA |
| 鉴权 | 自管凭证（02）+ OIDC 对接留 v1.1 | 独立部署优先自洽 |
| MCP | 官方 Python SDK，stdio+HTTP | 与 REST 同服务进程，天然同中间件 |

## 6. 演化挂点（v2 授权层如何长上来）

`directory/agent` 预留 trust_tier 字段位；`assets` 的定义 schema 预留节点级 `policy_ref`；audit_event 已带 policy_version_id 列位。v2 的风险策略层作为新的"第四面"（策略中心）插入同一配置管线——架构不推翻，只加面。
